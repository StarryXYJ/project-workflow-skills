# 项目规范与工作流

参考 Gal.Net 的 feature 流程，将需求、设计、实现、验证、审查和经验沉淀连接起来；根据任务规模裁剪，不强制创建全套文件。

## 先判断任务

1. 识别用户要的是制定规范、规划设计、实现、审查还是收尾；仅执行授权范围。实现请求本身即授权相关代码修改，单独的设计或审查请求不隐含实现授权。
2. 阅读项目指令、现有文档、相关代码与测试；修改前检查工作树，保护已有改动。已有流程和目录优先，用户要求优先于本 skill 的建议。
3. 按用户明确指定的流程选择；未指定时根据目标、范围和风险选择：较复杂的功能用 `feature`；边界清晰、风险可控的小到中等功能用 `quick`；针对明确缺陷的修复用 `hotfix`；按用户指定范围审查问题并分阶段修复用 `refactor`（重构）。简单任务保持轻量，纯问答或独立审查不强行进入完整流程。缺少会改变方案的关键信息时澄清，其余作明确假设继续推进。
4. 用户要求建立项目规范时，先盘点实际技术栈和已有实践，参考 [项目规范](references/standards.md) 提出适配方案；只在用户要求落地或工作需要时写入项目，避免覆盖已有约定。用户要求建立或检查 Git 基础配置时使用 `project-git-init`（若可用），遵循其编码、忽略规则和既有仓库保护原则。

## 执行与交付

- 按选定路径阅读 [feature](references/feature-workflow.md)、[quick](references/quick-workflow.md)、[hotfix](references/hotfix-workflow.md) 或 [refactor](references/refactor-workflow.md)。复用项目已有记录和约定；阶段可以独立使用，流程文件不是普通任务的实施门禁。
- 所有阶段计划先详细列出目标、任务、依赖、验证和退出条件；实施中每完成并验证一部分，就将完成部分简化为结果和证据并标记状态，保留未完成部分的详细计划。参见 [阶段计划与 Git](references/phase-and-git.md)。
- `feature` 和 `refactor` 每完成并验证一个实现阶段提交一次；`quick` 和 `hotfix` 全部完成并验收后提交一次。具体提交与 squash 边界见 [阶段计划与 Git](references/phase-and-git.md)。
- 保持职责边界，优先复用现有机制；避免无关重构。涉及接口、数据格式、迁移或生命周期时明确兼容性、失败和回滚方式。
- 选择能验证实际行为的检查，记录运行命令、结果和未覆盖范围；失败、环境障碍和未完成工作如实报告。实施中方案变化时同步必要记录。
- 根据实际代码和验证更新受影响的正式文档，使用 `project-docs-sync`（若可用）；整理可复用经验时使用 `project-lessons`（若可用）。两者也可独立调用；不可用时遵循本 skill 的文档和经验原则。
- 最终说明结果、关键决定、验证和剩余风险。审查请求以有证据的可操作问题为主，附位置和影响；无发现也说明验证范围。
