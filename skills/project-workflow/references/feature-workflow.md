# Feature 工作流参考

推荐顺序：需求 → 设计 → 阶段计划 → 实现与验证 → 审查 → 收尾。每一步可单独使用；小改动可以合并或省略步骤。明确采用 feature 流程时复用或创建 feature 记录；独立阶段或普通改动不强制创建，复用现有记录并避免重复。

## 需求

记录问题与目标、范围及非目标、约束、可观察的验收标准、假设和影响方案的开放问题。先查已有实现和相关记录；不把猜测写成用户决定。

## 设计

依据真实代码和依赖描述职责、数据流、接口、候选方案及取舍；对兼容性、迁移、失败处理、资源生命周期和风险按需说明。区分当前事实和提议，不为简单改动制造架构文档。

## 阶段计划

按依赖拆分可独立验证的纵向切片，最初详细列出各阶段目标、任务、依赖、验证方式及退出条件；避免无价值的微阶段。实施中每完成并验证一部分，按 [阶段计划与 Git](phase-and-git.md) 简化完成项并标记状态；计划变化时说明原因。用户只要求计划时不开始实现。

## 实现与验证

按可验证切片推进，每个实现阶段完成并验证后按 [阶段计划与 Git](phase-and-git.md) 提交一次，保持项目架构边界；对应变更补充必要测试和文档。验证结果应包含实际执行的命令或操作、通过/失败、范围与限制。若发现重大设计偏差，更新相关记录并按授权继续；关键需求不明时先澄清。

## 审查

对照需求、设计、实际 diff 和证据，重点检查行为、边界条件、兼容性、并发和生命周期、测试及文档。报告可定位的问题、影响和严重程度，区分事实与风险；审查请求默认不修改代码。没有发现也不等于证明没有缺陷。

## 收尾

总结实际结果、关键决定、验证证据、计划偏差、已知限制及后续工作。把已验证的稳定事实更新到项目正式文档，把过程留在 feature 记录；失败或未验证项保持真实状态。只记录有复用价值的经验，不把推测当作事实。

## 可选记录形式

对于需要持久追踪的工作，可采用项目已有 issue、设计文档或 feature 目录。若项目没有约定，可建议 `features/<id>/` 下按需保存 `feature.md`（需求）、`design.md`（设计）、`phase-plan.md`（阶段和验证）、`review.md`（审查）及 `summary.md`（结果）；合并或省略空文件。命名、状态和保存位置应适配项目，不预设编号或硬性门禁。

## 阶段状态

按项目约定记录计划、进行中、已验证或跳过；只有达到退出条件并有验证证据才标为已验证。存在阻塞、失败或未完成迁移时保留真实状态。仅要求单个阶段时，完成该阶段，不自动进入后续实现或发布。
