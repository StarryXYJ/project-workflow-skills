# 阶段计划与 Git

## 阶段计划

在开始实现前，详细列出所有已知 phase 的目标、具体任务、依赖、验证方法和退出条件；记录未决问题与风险。计划应足够指导执行，不需要预测无法得知的细节。确有新信息时更新计划并说明变化；重构流程中的新缺陷须先经用户确认。

实施时，每完成并验证一个部分，及时把该部分的详细施工计划简化为简短的完成结果、验证证据和状态；未完成部分保留详细计划。阶段仅在退出条件达到且验证有证据时标为完成；失败、跳过、阻塞或未验证项如实保留。不要删除仍有价值的决策、偏差、证据或待办；使用项目已有记录位置，避免覆盖用户内容。

## 提交

遵循用户更具体的指令和项目规则；使用流程时将其视为对本任务本地提交的授权。开始前检查 Git 状态、当前分支及基线，识别预存的暂存和未提交内容；只提交本任务变更，不能安全区分时先解决或询问。不得自动创建分支、推送、合并或发布，除非已获得相应授权。非 Git 工作区或提交失败时继续能做的工作，并说明无法提交的原因。

- **feature 和 refactor**：每个实现 phase 完成、验证并更新计划后，创建一个对应的本地提交。失败或未达到退出条件不作为完成阶段提交；收尾产生的必要改动单独提交或按用户选择纳入最终整理。
- **quick 和 hotfix**：完成全部实现、验收及必要文档与经验记录后，创建一次本地提交；不要每阶段提交。失败或无法验收时保留真实状态并说明，除非用户另有指示，不宣称完成。

feature 和 refactor 全部完成后，向用户提供选择：保留各阶段提交、不做 squash；按用户指定的阶段分组 squash 为多个提交；或将本任务提交 squash 为一个提交。若用户此前已明确选择，则遵循其选择；否则保留现有提交并等待用户选择，不默认重写历史。多个提交的分组由用户指定或先提出具体分组供确认。

squash 前确认基线及涉及的提交仅属于本任务，检查工作树与暂存区，保护原有改动；已推送、共享或含其他人提交的历史不自行重写。只有在用户选择并且安全边界明确后执行相应的本地历史整理，不强推；无法安全整理时保留提交并说明。
