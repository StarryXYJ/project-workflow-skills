# quick 工作流

源自 Gal.Net 的 feature fast-track，面向目标明确、影响可控、可快速验证的小到中等 feature。用户明确要求 quick 时采用；单独设计、审查或普通小修复不必强制建立 feature。若涉及重大架构或公共契约、复杂迁移、冲突的工作树改动、关键需求不清或缺乏可信验证，转入适当的 feature 流程，说明原因；用户只要求规划时不实现。

1. **设计规划**：检查项目规则、已有 feature、相关代码和工作树，复用既有记录。需要新建时遵循项目命名；轻量记录目标、范围、非目标、验收、关键约束、设计取舍和一到数个有验证与退出条件的切片；如有阶段计划，按 [阶段计划与 Git](phase-and-git.md) 先列详细计划，完成部分逐步简化。
2. **实现验证**：按授权推进可验证切片，保护已有改动，记录实际验证及状态；发现重要偏差时更新设计或计划。风险超过 quick 范围时转入 feature 流程。
3. **审查收尾**：风险较高或用户要求时进行独立审查；总结结果、证据、偏差、限制与后续事项，将已验证的稳定事实同步到对应正式文档，按需记录可复用经验。

显式采用 quick 并建立 feature 记录时，参考 Gal.Net 的 `feature.md`、`design.md`、`phase-plan.md`、`summary.md`，保持内容精简，并服从项目已有记录形式；有风险或要求时单列审查。quick 压缩流程而不降低验证标准；失败或阻塞不得标记完成，不合并无关任务。

全部完成并验收后按 [阶段计划与 Git](phase-and-git.md) 提交一次。
