# refactor 重构工作流

适用于用户指定代码范围，要求系统审查并分阶段修复缺陷或改进质量。遵循用户确定的范围；不把主观风格偏好当作缺陷。

1. **范围审查**：阅读项目约定、相关代码、测试和文档，检查逻辑正确性、边界条件、设计与可维护性、测试覆盖及其他与范围有关的问题。每项缺陷列出位置、证据、影响、建议方向及优先级；区分已证实问题和待验证风险，避免只列抽象建议。
2. **用户审查缺陷列表**：向用户提交列表，等待用户确认、调整或排除各项。用户确认前不开始依赖确认的修复；可以继续不依赖确认的只读调查。若没有发现可操作缺陷，如实说明审查范围，不编造问题。
3. **计划**：根据用户确认的缺陷编写详细阶段计划，每个确认的缺陷对应一个独立 phase，标明目标、任务、依赖、验证和退出条件；先考虑依赖顺序。发现缺陷有重叠或依赖时说明关系，不静默合并或扩大范围。遵循 [阶段计划与 Git](phase-and-git.md)。用户只要求计划时不实现；用户已要求完整执行并确认缺陷后，完成计划即可继续实现，无需额外确认计划，除非仍有关键决策待定或用户要求审查计划。
4. **实现与验收**：逐 phase 修复并验证，完成部分简化并标记状态，每个 phase 完成后提交一次。发现新增缺陷列为候选，不擅自加入已确认范围。验证失败或阻塞时保持真实状态。
5. **收尾**：总结每项修复、验证结果、限制及未处理问题；按 [阶段计划与 Git](phase-and-git.md) 让用户选择保留阶段提交、合并为多个提交或合并为单个提交。
