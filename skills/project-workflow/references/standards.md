# 项目规范参考

根据已有仓库和团队习惯选择，不要求复制目录或技术栈。制定规范时区分已存在的事实、建议和待决定事项，说明适用范围、责任和检查方式。

- **结构与边界**：定义模块职责、依赖方向、公共接口和资源所有权；沿用现有布局，避免为统一形式搬迁文件。变更公共契约时说明兼容性与迁移。
- **编码与变更**：使用项目现有格式化、静态检查和依赖管理方式；优先小而聚焦的改动，避免混入大范围格式化或无关重构。不要把个人风格升级为阻塞规则。
- **Git 与协作**：保护未提交改动，遵守仓库分支、提交、评审约定。推送、合并、发布等外部动作遵循用户授权和项目规则，不因使用本 skill 自动执行。
- **验证与 CI**：记录项目真实的构建、测试、静态检查入口及前置条件；按变更风险选择单元、集成、端到端或人工验证。测试实际行为和边界，报告环境限制；CI 的通过范围不等于所有平台已验证。构建产物、临时文件遵循现有输出和忽略约定。
- **文档分工**：一个事实尽量只有一个权威来源。当前契约放规范，实际操作放手册，一次性目标、设计取舍及过程放 feature 记录；agent 的可复用经验放项目约定的知识位置。目录名仅是建议，遵循项目实际结构。
- **经验管理**：遇到可复用的非显然问题，记录现象、证据、根因或假设、适用范围和解决方法；经验证再提升为长期规则。避免记录秘密，把一次偶发故障推广为全局规范，或堆积重复经验。

新项目可从结构、运行/验证入口、变更约定和文档位置起步；规模和风险增长时再增加更细的约束。不要引入未经请求的工具、部署流程或平台支持承诺。
